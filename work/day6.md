```text

```

若项目采用 Markdown 转 PDF，第一版 PDF 建议输出到 `drafts/review-integrated-v1.pdf`，生成方式、字体和命令另记在 README 或会议记录中，避免不可复现。

## 二、完整 Review 结构与负责人

整合稿采用以下结构：

| 章节 | 主整合人 | 第二核查人 |
|---|---|---|
| 摘要、引言 | A | C |
| 问题定义和研究意义 | A | B |
| 相关研究 | C | A |
| 论文主要结果 | A | B |
| 核心技术直觉 | B | C |
| 数据结构详细实现 | B | A |
| 正确性证明 | B | A/C |
| 时间和空间复杂度证明 | A+B | C |
| 技术优越性 | C，A/B 提供证据 | A |
| 局限性与适用范围 | C | B |
| 后续研究 | C | A |
| 小组评价、结论 | 三人共同 | 轮换复核 |
| 参考文献 | C | A/B 抽查 |

每章开头不得保留个人草稿的作者提示；个人贡献通过 Git 历史、PR 和贡献表记录，而不是破坏正文连贯性。

## 七、普通读者测试

三人分别选择非本人主负责章节：A 测试实现章，B 测试相关研究章，C 测试问题/下界章。每人回答：

1. 是否定义了全部符号；
2. 能否仅根据文字重画数据结构或证明依赖图；
3. 是否解释每一步为何需要；
4. 贯穿示例是否与一般证明明确区分；
5. 能否找到对应原文位置；
6. 是否存在结论先于解释；
7. 是否把直觉、黑盒接口或实验观察误写成正式证明。

每人至少留下 5 条读者测试意见，作者回应后由第三人抽查关闭。

## 八、全文一致性检查

### 数学与技术

- 全文 `log` 底数、区间、取整符号和下标一致；
- `n` 明确是当前大小还是插入次数，重复插入口径一致；
- `ε` 与 `δ` 不混用；
- Theorem 10 的正式条件只出现一个统一版本；
- 教学示例不承担一般概率、空间或正确性证明；
- Q1/Q3 警告在正文、脚注或问题清单中可见。

### 语言与结构

- 英文术语首次出现给出中文解释，后文用法统一；
- 删除三章拼接造成的重复背景和重复结论；
- 每章开头承接前文，结尾说明下一章需要什么；
- 摘要不包含正文未证明或未引用的结论；
- 小组评价明确区分事实判断和观点。

### 图表与引用

- 图表编号、标题、正文引用和来源完整；
- bibliography 中无未引用条目，正文无缺失条目；
- DOI、作者、年份、会议/期刊、预印本状态一致；
- PDF 页码与论文印刷页码的口径在核查报告中说明。
